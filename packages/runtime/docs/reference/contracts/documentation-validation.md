# Documentation Validation Contracts

DocsFab selects documentation validation from verified repository, patch, candidate, and host policy evidence. Repository configuration and model output cannot select a validator, command, backend, or check ID.

New source-aware delivery uses `DocumentationValidationBindingV2` and profile version `"2"`. The documentation profile runs these checks in order:

1. `candidate-input-tree`
2. `documentation-source-applicability`
3. `documentation-paths-readable`
4. `documentation-relative-links`
5. `documentation-navigation-targets`
6. `isolation-boundary`

Every check must produce exactly one result. A missing, duplicate, or extra result fails validation. The result digest binds the ordered results, validation state, check set, candidate tree, and source applicability digest.

The applicability record binds the repository identity, base revision, candidate input tree, changed path statuses, and sorted source roots. Each root records its adapter, verified configuration digests, navigation mode, required path closure digest, and limitations. Plain Markdown passes navigation only after the host records an affirmative `none` navigation mode. Fern continues to use its existing route checks through the generic navigation result.

Preflight derives the applicability over the candidate that delivery validates: the run base plus the verified patch. It builds a private copy under the DocsFab state root (`validation-candidates/`, beside the run store) the way delivery builds its candidate: the base tree is read into a private index, the patch is checked and applied with `git apply --cached --binary`, and the index is checked out into the copy. A private Git directory borrows the run repository's objects through its `objects/info/alternates` file, so preflight writes no worktree, index, ref, or object to that repository, and it removes the copy whether or not derivation succeeds. `validation-candidates/` must be a real directory that the operator owns; a symbolic link or anything else there refuses with `validation-candidate-unavailable` and is never followed. A copy that an interrupted preflight leaves behind stays in `validation-candidates/`, because preflight removes only the copy it created; remove leftover `candidate-*` directories by hand when no publication is running. Each preflight therefore materializes the base tree once more. Reading the base tree, checking the patch with `git apply --check`, and checking out the copy are each bounded by `delivery.validationCandidateCheckoutTimeoutMs`; a command that outlives it refuses with that limit's code. Only `git apply --check` exiting with status 1 falls back: preflight then binds the operator checkout as earlier builds did, and delivery runs the same check and refuses first with `patch-conflict`. Any other failure to build the copy, including another exit status, refuses with `validation-candidate-unavailable`. Delivery re-derives the record from the delivery worktree and refuses with `invalid-delivery-input` when the digests differ. Both sides compute the candidate-input and repository-identity digests through one shared helper. A version 2 plan bound by an earlier DocsFab build named the operator checkout and a different digest encoding, so delivery refuses it; start a new run to publish that change.

Relative CommonMark and GFM fragments are percent-decoded and then compared literally with the rendered anchor ID. ATX and setext headings outside fenced and indented code use the repository's normalized section-link convention: inline formatting and HTML tags are removed, punctuation is discarded, spaces become hyphens, and repeated heading IDs receive `-1`, `-2`, and later available suffixes. Inline code text remains part of the heading. Literal HTML `<a id="...">` and `<a name="...">` anchors use an exact normalized-Unicode comparison and do not change repeated-heading suffixes. Renderer-specific label and explicit-heading extensions are not treated as plain Markdown anchors.

The fixed adapter registry contains `plain-markdown`, `mkdocs`, `docusaurus`, `sphinx`, `fern`, and `jupyter-book`. Each adapter declares its configuration file spellings, markup extensions, and one state (`supported`, `partial`, `unsupported`, or `not-applicable`) for each capability: `detect`, `navigation`, `routes`, `versions`, `includes`, `components`, `frontmatter`, and `validate`. Applicability, profile selection, and repository inventory recognize generator configuration only from this registry. This release validates plain Markdown, the bounded MkDocs/Material subset (see [documentation-sources-mkdocs.md](documentation-sources-mkdocs.md)), the bounded Docusaurus MDX subset (see [documentation-sources-docusaurus.md](documentation-sources-docusaurus.md)), the bounded Sphinx RST and MyST subset (see [documentation-sources-sphinx.md](documentation-sources-sphinx.md)), and Fern. Jupyter Book's `validate` capability is `partial`: a root with `_toc.yml` or `_toc.yaml` and no other generator configuration is a `jupyter-book` root that runs the plain-Markdown link and path checks and records the advisory `navigation-not-checked` limitation, because its table of contents is not validated. Advisory limitations do not stop validation; every other limitation does. A generator that validates natively owns the root over Jupyter Book, so a Sphinx `conf.py` beside a sphinx-external-toc `_toc.yml` stays a Sphinx root, and deleting `_toc.yml` is not a configuration downgrade.

Historical version 1 plans, bindings, receipts, check IDs, and digests retain their original meaning. Readers decode them without converting `fern-navigation-targets` into a generic pass. Start a fresh preflight before a new delivery mutation so the host selects current applicability and version 2 checks.
