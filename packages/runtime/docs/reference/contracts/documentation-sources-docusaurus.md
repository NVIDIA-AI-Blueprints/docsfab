# Docusaurus Documentation Source Contract

DocsFab recognizes a Docusaurus documentation root through
`docusaurus.config.{js,cjs,mjs,ts,cts,mts}` or `sidebars.{js,cjs,mjs,ts,cts,mts,json}`
at the root or a nested package boundary, reusing the shared adapter registry in
[`documentation-source-support.ts`](../../../src/repository/documentation-source-support.ts).
Every recognized file is bound into the applicability record. Validation parses
only the `.js` and `.ts` spellings; a root whose only sidebars use another
spelling reports a `documentation-navigation-targets` limitation. A
`docusaurus.config.{cjs,mjs,cts,mts}` file is bound but not parsed, so its
literal-grammar check is skipped without a limitation; this is known debt
tracked on #1595.
The shared registry `validate` capability for `docusaurus` is `supported`: a root whose
governing configuration and sidebars parse within the finite literal grammar
below derives an empty `limitations` array from
`deriveDocumentationSourceApplicability` and reaches the real validator arm
through the ordinary, registry-gated path (see
[documentation-validation.md](documentation-validation.md)). The end-to-end
proof lives in
[`test/documentation-source-docusaurus.test.ts`](../../../test/documentation-source-docusaurus.test.ts),
which drives `deriveDocumentationSourceApplicability` directly against the
fixture tree rather than hand-building applicability records.

## Supported literal configuration grammar

`docusaurus.config.js`/`.ts` and `sidebars.js`/`.ts` are parsed with a bounded,
hand-rolled tokenizer in
[`documentation-source-docusaurus.ts`](../../../src/repository/documentation-source-docusaurus.ts)
that never evaluates source. Exactly one governing statement is required:

- `module.exports = <literal>;`
- `export default <literal>;`
- `export default <identifier>;` where `<identifier>` resolves to the one
  supported local `const <identifier> = <literal>;` binding.

A `: Type` annotation on that one local binding is skipped without validation.
`import type ...` statements, and named imports where every specifier carries
the `type` modifier, are stripped without evaluation. Top-level `type ...` alias
and `interface ...` declarations are also skipped. A non-type-only import is
tolerated only while its local binding is never referenced by the exported
value; referencing it fails closed with a stable, greppable parse error.

Literal values are strings (single, double, or template-literal without a
`${...}` interpolation), numbers, booleans, `null`, arrays, and objects with
identifier or string keys. Function calls, `...` spread syntax, computed
`[expr]:` object keys, and property-access member expressions in value position
are rejected with distinct error messages. More than one local literal
constant binding, more than one governing export statement, or no governing
export statement at all are also rejected.

## Supported sidebar item shapes

A parsed sidebars value must be a literal array (one implicit `default`
sidebar) or a literal object keyed by sidebar name, each value a literal array
of items:

- a literal string, or `{ type: "doc", id: "<string>" }`;
- `{ type: "category", label: "<string>", items: [...] }`, recursively;
- `{ type: "autogenerated", dirName: "<string>" }`;
- `{ type: "link", label: "<string>", href: "<string>" }`.

Any other `type` value is an unsupported sidebar item type and fails closed.

## Document reachability

A changed `docs/**/*.md`/`.mdx` file is reachable when its id (the frontmatter
`id:` scalar, else its docs-root-relative path without extension) appears in
the flattened sidebar doc-id set, or when its docs-root-relative directory
matches (or descends from) a flattened `autogenerated` `dirName`. An
unreachable changed document fails the `documentation-navigation-targets`
check; this is the honest "needs a navigation update" signal for this bounded
slice; multi-page authorized-update workflow semantics live in the delivery
and publication layers outside this adapter Path scope.

Relative link and anchor validation on a changed doc reuses the existing
generic Markdown link/anchor machinery, so opaque MDX syntax (component
imports, JSX expressions, `<Tabs>`/`<TabItem>` boundaries) is preserved and
never evaluated: none of it matches the finite link/anchor/Card patterns those
functions already check. Absolute Docusaurus routes (`/docs/...`) are not
resolved in this bounded slice; only relative file links validate. A changed
markup path outside the configured docs root (for example a root `README.md`,
or any file under a custom non-`docs/` directory) never reaches this
validator arm at all: `documentation-source-applicability.ts`'s
`mixed-root-ownership` guard (docusaurus owns only paths under `docs/`)
attaches that limitation to the root, and the caller's own top-level
limitation gate rejects the whole delivery with `documentation-source-
applicability`/`limitation` before any adapter-specific check runs. That is a
fail-closed outcome, not a silent pass, and it is proven through the real
`deriveDocumentationSourceApplicability` path in the test suite, not asserted
against a hand-built record. An unrelated, unchanged broken document
elsewhere in the same docs tree never blocks validation of the actually
changed documents.

## Exact supported and unsupported cases

| Case | Result |
| --- | --- |
| `module.exports = {...}` literal object/array, nested categories, autogenerated dirs, doc ids and slugs | Supported |
| `export default <local literal binding>` with a stripped type annotation | Supported |
| `import type {...} from "...";` and fully-type named imports | Supported (stripped) |
| Preserved MDX imports, expressions, and `Tabs`/`TabItem` boundaries in doc bodies | Supported (opaque, unevaluated) |
| Function calls (including `require(...)`), spreads, computed keys | Unsupported: `documentation-navigation-targets` limitation |
| A referenced non-type-only import | Unsupported: `documentation-navigation-targets` limitation |
| A changed doc unreachable from every sidebar | Failed: `documentation-navigation-targets` |
| A relevant parse failure in `docusaurus.config.js`/`.ts` or `sidebars.js`/`.ts` | Limitation, distinct from an unrelated unchanged failure elsewhere |

## Native-build qualification recipe for Q1 (#839)

The registry `validate` capability is `supported` and the paired assertion in
`test/documentation-source-support.test.ts` reflects it. Remaining promotion
work for full native-build qualification: (1) add `"docusaurus"` to any
adapter allowlists in the delivery/publication layers that still special-case
`plain-markdown`/`fern`; (2) run the qualification matrix corpus (C2, #830)
against this adapter under the same isolation bounds as the other four
adapters. No live provider spend, native build, or publication is authorized
by this document.
