# Native Product Feedback Materialization

Use this path for a registered source case or genuine merge decision whose
offered delta changes one existing claim's statement and scope, and for a
consistent input that changes no claim. Every path writes one complete,
immutable model version with reproducible bytes. The package's own freshness
checker validates that version, and the approved-model projector reads it.

## Bind the Inputs

Read the current approved baseline through its host reader. Read C's complete
comparison through the persisted evidence reader and D's decision through
`readVerifiedModelConflictDecisionSource`. Genuine merge comparisons instead
use `readVerifiedMergeDecisionSource`, which returns a distinct
`docsfab-verified-merge-decision-source` envelope. The host adapter resolves the
registration through the actual authority stores and rechecks the approved
generation after reading Git. A comparison's case kind does not determine the
original decision-source lineage.

The merge envelope retains the original continuation, question, answer,
registered source, custody digest, and semantic offer persisted before the
reply. Its separate `sourceRegisteredAt` is the actual legacy registration
time. It is never converted into a model case. The verifier selects the exact
C decision using the offer's `findingSha256`, then checks the approved parent,
complete prior claim, selected core, source versions, merge anchor, comparison
identity, and offered approval target. Separate file assessments can concern
the same claim; their matching claim IDs alone do not identify the decision.

The derived source artifact retains those original binding identifiers,
the immutable continuation anchor, and the offer digest. The current
continuation envelope is validated but its changing revision/status digest
does not enter generated bytes. Saving the final continuation state therefore
does not invalidate a candidate produced from the same accepted owner source.
The artifact does not contain the protected raw reply. Parsing or
reproducing serialized content grants no owner authority; the host's actual
source reader and F's current-authority checks remain required.

After an actual rescope reply, the legacy continuation may carry a fresh
source-case analysis and a second owner question. Its new offer must include
`comparisonCase` naming the exact current case and `reanalysisOf` naming the
earlier question and registered rescope source. The original merge anchor and
conflict remain intact. E verifies the earlier turn, stable claim/variant
slots, current comparison receipt and new answer. An earlier answer cannot
approve the new delta. Offers without these fields retain their original
direct-merge meaning; missing or mismatched lineage refuses reproduction.

The earlier turn may instead be an explicit owner-information request and
registered `provide-evidence` or `rescope` reply. E validates its distinct
information/request hashes, cited evidence, original baseline and claim,
without constructing an earlier offer or options. The information-only source
cannot approve a candidate. Only the later exact accepted semantic offer can
support reproduction, with `reanalysisOf` pointing to that actual earlier
request/source.

The comparison receipt is `outcome.outcomeSha256`, which binds the complete
outcome, decisions, citations, execution receipts, and coverage. The stable
`comparisonSha256` and the serialized artifact digest are separate identities.
An issue source can support proposed intent; issue closure does not establish
shipped behavior.

Preserve every field of the original claim except its explicitly offered
`statement` and `scope`. Its full `beforeClaimRecordSha256` must match the
approved baseline. This contract does not add or delete claims, change approval
metadata, resolve unrelated conflicts, or modify retained evidence.

A matching registered owner decision is reused. Missing or wrong-scope
approval still allows a reviewable candidate, but cannot produce a promotion
proof: its report records the conflict as `open` with disposition `none`.
`keep-approved` also writes a new version. Its change record is the approved
claim unchanged, and its report records the decision that upheld it. It keeps
the corrective implementation proposal under
`.docsfab/reference-model/proposals/<recipe>.json` as the builders' work item.
That proposal does not establish that an implementation change or behavior
test occurred.

## Configure Exact Claim Routes

The host configures each claim's target ID, path, delivery surface, H2 heading,
and exact initial paragraph. Requests cannot remap an approved target ID.
For example:

```json
{
  "claimId": "CLAIM-MENTION",
  "targetId": "product-requirements",
  "path": "planning/product-requirements.md",
  "delivery": "repository-planning",
  "heading": "Mention Requirement",
  "beforeText": "Ordinary channel messages require an explicit mention."
}
```

These are examples of independently configured targets:

| Target | Example Path | Delivery |
| --- | --- | --- |
| Product requirements | `planning/product-requirements.md` | Repository planning |
| Software requirements | `planning/software-requirements.md` | Repository planning |
| Plan of record | `planning/plan-of-record.md` | Repository planning |
| Public requirements | `docs/specifications/behavior.md` | Public documentation |

Paths and headings are product configuration. Planning files are not assumed
to be public-site pages. Unknown or changed routes return
`needs-target-route`; they do not authorize a broader paragraph replacement.

The model package itself is always written, so a decision needs no document
route. The reserved approval-target ID `product-reference-model`
(`PRODUCT_REFERENCE_MODEL_TARGET_ID`) names the package in an approval scope.
It is never a route ID. The recipe's routes must equal the approval scope with
that ID removed:

- A PRM-only decision carries no routes and the scope
  `["product-reference-model"]`.
- A partial projection names the package and exactly the documents it
  updates, for example `["product-reference-model", "product-requirements"]`.
- A scope that names a document the recipe does not write is refused.
- Scopes without the reserved ID keep their earlier meaning: every scope
  target is a written route.

The host seals the reserved ID into every merge-decision offer, then exactly
the documents the retained comparison's projection updates. No configured
document target may take the reserved ID. The host's governed-convergence path
reads the same token in adjudication affected targets, where it also names the
package but derives all three reference projections from it. An approval scope
is never resolved through that derivation.

On the first update, the materializer replaces the one exact configured
paragraph inside the named H2. It preserves sibling paragraphs, subsections,
frontmatter, links, and the rest of the file. The replacement contains the
new substantive claim and scope, with explicit candidate and behavior-evidence
status. Claim-specific markers delimit this generated region for later
updates; they are not a provenance appendix around unchanged contradictory
wording.

Later updates accept only the bounded prior rendering of the same approved
claim and scope. A manual edit inside the generated region requires
reconciliation instead of being discarded. Ambiguous headings, duplicate
paragraphs, and selectors inside fenced examples or comments refuse.

## Retain Immutable Model and Source History

The candidate lives at
`.docsfab/reference-model/shared/<model>/<version>/model.md`. Its strict native
marker is `docsfab-product-feedback-model:v1`. It declares its actual approved
parent, one complete replacement claim (or `change: null` for a record-only
version), retained files and conflicts, and the derived source registration.
The canonical projector returns the same `docsfab-reference-model-snapshot`
shape for legacy and native versions.

Every version is complete. Materializer `v2` writes:

- `<version>/model.md`, `<version>/inconsistency-report.md`, and
  `<version>/merge-receipt.md`
- one source thread with one item, event ledger, retained artifact, and view
- a `history.md` row inserted first under the table header
- the three "Current DocsFab model" links in
  `.docsfab/reference-model/README.md`, pointed at the new version
- for `keep-approved` only, the corrective proposal JSON

The report and receipt are rendered from the recipe, the approved parent, and
the registered decision. They cite custody and never content. The conflict ID
is `CONFLICT-` followed by the merge question's conflict ID with its
`conflict-` prefix removed; a model-case or undecided change uses a
digest-derived `CONFLICT-FEEDBACK-<suffix>`. The adjudication names the
answering principal, the decision source kind and authority receipt, the
answer time, `accept-variant`, and the protected custody digest; the original
reply is not reproduced. Its `decision_evidence` is the version's registered
item and its `resulting_claim_ids` is the changed claim. Inherited open
conflicts are listed by ID and source path, unchanged. Receipt sections 1
through 13 follow the synthesis contract, and section 14 carries the legacy
ancestor's visual-closure receipt block byte for byte, or states that the
ancestor has none.

Select the next available version from the exact Git inventory. An unapproved
candidate still occupies its immutable path. For example, approved v0.28 can
produce v0.30 when v0.29 already exists; the parent remains v0.28. The approval
stream advances by one independently of the version suffix. No legacy merge
ID, visual closure, or approval state is fabricated.

Each candidate adds its own deterministic source thread. It retains the
offered source-version descriptors and a derived decision artifact referring
to the protected original custody. It does not reconstruct an owner's raw
Slack wording. Existing thread, item, event, artifact, and ancestor model
bytes remain exact. Unresolved conflicts remain inherited.

## Record a Consistent Input

A complete, current comparison that found no load-bearing conflict produces a
`record-only` version without a decision. Its recipe carries
`proposal: null`, no routes, and the input's source versions; it must be
materialized with `decision: null`. The version inherits every parent claim
unchanged. Its report states that no inconsistencies were found and records no
conflict or adjudication. Its source thread observes the input: the thread's
origin kind is `repository-issue` when every source is an issue version and
`repository-merge` otherwise, and its item type is `source-observation`.
`requiresOwnerApproval` is false, so the version verifies for publication.

A record-only recipe with a decision, a route, or no source version is refused.
A recipe that proposes a claim change without a decision is not record-only:
it produces an unapproved candidate that cannot verify. Adding a new claim
from a conflict-free input needs a comparison-contract change and is not
supported here.

Replay uses the recorded metadata timestamp and the same recipe. It does not
read the current clock or allocate new identifiers. Binary retained artifacts
use the exact-byte codec: UTF-8 strings or
`{"encoding":"base64","data":"..."}`. Hashes and Git blob IDs cover the
decoded bytes, including byte order marks and binary content.

## Reproduce Before Publication or Promotion

The knowledge `runtime-adapter.mjs` exports
`materializeProductFeedbackCandidate`, `verifyProductFeedbackCandidate`,
`encodeProductFeedbackFile`, `productFeedbackTargetRoutePolicySha256`, and
`assertProductFeedbackTargetRoutes`. Typed host consumers use the exports from
`reconciliation/convergence-runner.ts`.

`parseProductFeedbackCandidateManifest(value)` synchronously validates a closed
manifest and recipe without reading a baseline or Git. It checks nested data
shapes, source-version records, recomputable hashes, declared bindings, safe
repository paths, and the exact generated/required file layout. It returns
frozen data. It does not authenticate the declared currentness, external route
policy, approval, or actual file bytes; those still require the trusted
readers and full reproducer. Archive callers retain their raw credential,
key and host-path screening, and may exempt only known prose leaves from
excluded-word screening after this structural validation.

Normal ingress uses `createProductFeedbackRuntimeConvergence` with its existing
project-bound runtime client. It reads the registered merge decision through
the runtime readers, the no-offer advisory reader first and then the offer
reader, before generating candidate bytes. It needs no promotion-role client.
The operator's `createProductFeedbackSourceCaseConvergence` continues to use
the authority-only source readers. Both produce candidates; F separately
rechecks current source authority before publication or baseline promotion.

Operator verification of a retained C entry uses the pure host helper
`verifyProductFeedbackComparisonEvidence({baseline, recipe, entry, decision})`.
It checks the actual outcome and artifact digests, original baseline/source
bindings, offered claim, D case receipt, and merge anchor when applicable.
Current observation, repository, and policy checks remain separate F gates.

The materializer returns the full model/source file map, actual changed target
bytes, expected claim records, and a candidate manifest. The manifest binds
the baseline generation and digest, base revision, target-route policy,
offered delta, decision registration, deterministic recipe, model blob,
source closure, and requested successor. Its publication receipt remains null
and its model state remains candidate.

F supplies actual immutable Git bytes to the verifier:

```javascript
assertProductFeedbackTargetRoutes({ manifest, routes: protectedCurrentRoutes });
const proof = verifyProductFeedbackCandidate({
  baseline: currentApprovedBaseline,
  decision: actualVerifiedDecisionSource,
  manifest,
  files: {
    base: actualBaseRevisionFiles,
    candidate: actualPublishedRevisionFiles,
  },
});
```

`requiredBasePaths` names present parent/source/document files plus the
history and model indexes; hosts read exactly
`requiredProductFeedbackBasePaths({ baseline, recipe })`.
`requiredAbsentBasePaths` names every new artifact and must map to null at the
base revision. Absence requires successful Git tree enumeration; an unreadable
object is an error. `requiredCandidatePaths` names the complete reproduced map.
No caller-supplied before-content or verification flag replaces these reads.
The `v2` manifest parser refuses any other materializer version and enforces
each disposition's write set: `generatedFiles` is the absent paths plus the
routed documents, `history.md`, and the model index. The verifier admits every
disposition except `unapproved`.

F separately checks the current protected route configuration, current source
and comparison evidence, actual owner authority, published tree, and exact
changed-file set. The publication manifest's files must equal E's
`generatedFiles`, so an extra edit outside the reproduced map cannot ride
along. Repository merge evidence and rendered-site delivery remain separate
gates. Byte reproduction does not grant either authority.

## Check the Result

Run the focused materializer and native-projector tests, followed by the owned
package checks. The native fixture exercises the actual retained v0.28 model,
two successive native versions, occupied-path refusal, binary source closure,
and the repository's Fern heading gate plus parsed Markdown link checks. For a
replacement, a PRM-only decision, `keep-approved`, and `record-only`, it also
runs the package's freshness checker and the projector over the resulting
v0.30. Its decision and source-store authority is explicitly synthetic.

`check_freshness.py` recognizes a native version by its marker. It validates
the exact envelope rendering, the version and parent binding against
`history.md`, the registered source item, the report's conflict records and
adjudication, and receipt sections 1 through 13 (and 14 from v0.29). It checks
that section 14 carries the legacy ancestor's receipt block unchanged instead
of running the visual-closure validator. The checker validates record
completeness; publication authority still comes from the verifier.

For actual public content or navigation changes, follow the repository's
documentation guidance: run `make fern-check`, the Fern H1 check, and
`fern docs broken-links --strict` over the resulting pages. A provenance digest
or a fixture's passing result does not attest a published site.
