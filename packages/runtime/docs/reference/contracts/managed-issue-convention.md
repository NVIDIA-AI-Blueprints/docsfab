# DocsFab-managed issue convention

DocsFab-managed issues are ordinary GitLab issues with a visible convention and
a content-free machine identity. The convention is provider-neutral: it does
not require native GitLab epics, expose credentials to a model, or make tracker
text part of authorization.

The current convention and marker schema version is `1`.

## Visible convention

New managed issues use one of these prefixes:

- `[DocsFab][Saga]`
- `[DocsFab][Epic]`
- `[DocsFab][Task]`
- `[DocsFab][Investigation]`

Every new issue has exactly one label from each controlled category, plus the
durable `docsfab-roadmap::managed` label:

| Category | Values |
| --- | --- |
| gate | `gate::g0`, `gate::g1`, `gate::g2`, `gate::g3`, `gate::g4`, `gate::g5` |
| workflow | `workflow::release-documentation`, `workflow::documentation-health`, `workflow::content-repair`, `workflow::information-architecture`, `workflow::investigation` |
| priority | `priority::p0`, `priority::p1`, `priority::p2` |
| lifecycle | `lifecycle::filed`, `lifecycle::ready`, `lifecycle::selected`, `lifecycle::in-progress`, `lifecycle::in-review`, `lifecycle::verified`, `lifecycle::closed`, `lifecycle::blocked`, `lifecycle::duplicate`, `lifecycle::superseded`, `lifecycle::manually-detached` |

Gate labels are the closed, lowercase tracker projection of maturity gates
`G0` through `G5`. Blocking is expressed by lifecycle, and a need for human
input is expressed by the required-human-input section; neither is overloaded
onto the maturity gate.

The lifecycle used by autonomous delivery is `filed → ready → selected →
in-progress → in-review → verified → closed`. A blocked, investigation-only,
duplicate, superseded, or manually detached issue is not eligible for a write
workflow merely because its marker still exists.

Saga, epic, task, and investigation relationships use standard issue IIDs.
This provides an issue-based hierarchy on GitLab installations where native
epics are unavailable.

## Hidden identity marker

Each description contains one canonical HTML comment generated by
`renderManagedIssueMarker`. Its JSON object contains only:

- the schema version;
- an opaque digest of the tracker repository key;
- the versioned managed semantic-finding fingerprint; and
- a canonical identity checksum.

The marker never contains repository or host paths, repository content,
credentials, prompts, evidence prose, or model output. Its checksum detects
accidental changes; it is not a signature or authorization. Reconciliation
must validate it against the current RoadmapLedger identity. A public rehash of
substituted fields does not make the marker match that ledger.

The managed finding fingerprint is not the RoadmapLedger's revision-bound
`finding.fingerprint`. Version 1 hashes the finding source, category, sorted
affected paths, and sorted semantic evidence keys. Production roadmap planning
derives each semantic evidence key as a full SHA-256 of a domain-separated
canonical candidate-ID record; arbitrary or truncated evidence keys are
rejected. Boundary IDs, repository
revision, evidence bytes/digests, rank, severity, and human wording are excluded.
The stable marker therefore does not change when the same semantic defect is
observed at a new tested revision with new evidence.

Immutable revision, repository-state digest, ledger digest, and tested revision
live in a separate content-free state binding. Public reconciliation accepts
only the current exact binding for patch generation. A valid stable marker with
a different state binding is classified as `migration`, but the result contains
no patch and no next-state binding. The convention exports no prior-state proof,
receipt, callback, or capability issuer. The live execution layer in #106 must
authenticate the exact tracker identity and issue IID against an immutable prior
ledger record and bind the prior/current state before any advance. A copied or
fully rehashed state binding is therefore inert caller data: it can request host
migration review, but it cannot authorize adoption or mutation. Terminal
duplicate and superseded issues remain terminal across revisions.

## Issue template

`renderManagedIssueDraft` emits the same required sections for every kind:

- Evidence
- Tested revision
- Rationale
- Audience impact
- Path scope
- Workflow
- Acceptance
- Verification
- Dependencies
- Required human input

Evidence is represented by sanitized references rather than source content.
Path scope is repository-relative. Every managed creation and controlled-label
update is bound separately to the exact Roadmap mutation-plan
v2 operation key, idempotency key, proposal digest, private material digest and
byte count, stable marker digest, and current state-binding digest. Creation
material is the exact issue-lifecycle create material derived from the canonical
rendered `ManagedIssueDraft`. Controlled-label update material is the exact
`add-labels` or `remove-labels` delta recomputed from a `ManagedIssuePatch` and
the current observation. The same material digest and byte count are consumed
by v2 execution. Title, prose, assignee, milestone, confidentiality, path, or
caller-supplied label expansion changes the material or is rejected before
binding. The model-facing record
therefore does not need the private mutation material or GitLab credentials.
Parent-IID relationships are separate link operations validated by
`validateManagedIssueHierarchyLink`; they are rejected as unbound create
material.

## Hostile-input and size boundary

Every public convention validator consumes passive JSON-shaped data only.
Proxy objects, accessors, custom prototypes, symbol properties, hidden
properties, sparse arrays, array subclasses, extra array properties, and
cyclic graphs are rejected from property descriptors without invoking caller
code. Declared array length is checked before elements are copied.
All exported kind, gate, workflow, priority, lifecycle, disposition, and
human-owned-field tuples are frozen runtime authority; callers cannot extend
accepted values or alter terminal lifecycle classification by mutating an
export.

Reconciliation accepts at most 10,000 observations, matching the read-only
GitLab reader's bounded 100-page by 100-issue authoritative scan. An observation
may contain at most 128 labels and 64 assignees. Template limits are 64 evidence
references, 256 paths, 128 acceptance items, 128 verification items, 128
dependencies, and 64 human-input items. Standalone semantic findings accept at
most 256 paths, evidence keys, and dependencies. Delegated Roadmap ledger and
plan arrays are bounded at 10,000 items with an aggregate 100,000-node and
32-level passive-data preflight. Required evidence, path, acceptance, and
verification arrays must contain at least one nonempty item; intentionally
empty dependency and human-input sections render an explicit `None.` item.

## Reconciliation and human ownership

Identity matching never depends on title or descriptive prose. Humans may edit
the title, prose, assignees, milestone, due date, weight, confidentiality, and
non-DocsFab labels. A schema version 1 reconciliation patch can contain only a
controlled-label correction that retains every human label. Revision migration
is deliberately inert here; #106 may advance the separate state binding only
after host authentication, without rewriting the description or stable marker.

An unmarked lookalike is reported as ignored and receives no patch. Removing
`docsfab-roadmap::managed`, or applying `lifecycle::manually-detached`, detaches the
issue without deleting its audit identity. Two active issues with the same
exact identity produce an explicit conflict.

Duplicate and superseded issues remain discoverable through their marker and
lifecycle label but are not replaced automatically. Migration, duplicate,
superseded, and manual-detachment are distinct typed reconciliation
dispositions; none grants mutation authority.
